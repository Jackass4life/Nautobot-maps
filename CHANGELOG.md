## [Unreleased]

### Added
- **An Admin page, and sharing a status page from Availability** (#530): what the API can do, the web pages can do too. Admins find **Admin** in the ☰ menu: API tokens (the active ones newest first, a search past 25; **New token** with role, a tenant picked from Nautobot's for a status token, and expiry, its key shown once with **Copy**; **Revoke** per row; "+N revoked or expired" with **Purge**), **Send test** for notifications with each channel's result, and **Check now** for the wireless controllers. On Availability, **Share…** next to a tenant makes a customer link (its key shown once) or replaces a leaked one. Sections with nothing to show are left out; operators and viewers see nothing new. `GET /api/page-config` answers `admin` (null for non-admins), and `GET /api/tenants` (admin) lists Nautobot's tenants
- **The API does what the command line does** (#529): `GET /api/status-links/<tenant>` (a tenant's status page link, as `status-link`; 404 for a tenant Nautobot doesn't have), `POST /api/status-links/<tenant>/replace` (as `status-link --new`: the old link stops at once, the tenant's tokens keep working) and `POST /api/wireless/check` (as `wireless-check`, one result per controller: reachable, signed in, access points seen and matched, the error in plain words; one check at a time). All admin. A test keeps every everyday command paired with an API route. `wireless-check` now says why a controller can't be read in plain words too
- **`token purge`** (#528): `python -m nautobot_maps token purge` deletes revoked and expired API tokens for good, never an active one; `--older-than DAYS` only those that stopped working longer ago, `--dry-run` lists them. Their names are free again; cases and maintenance windows keep their `token:<name>`. Also `POST /api/tokens/purge` (admin), with `older_than_days` and `dry_run`
- **Access points onboarding with Plug and Play** (#534): with Catalyst Center, an access point in Nautobot that isn't in the controller's inventory yet but is in its Plug and Play list shows in the map's site panel as "Onboarding (PnP: Unclaimed)" or "PnP error" with the reason, instead of "not in a wireless controller". Read in bulk with the access points (`onboarding/pnp-device`, pages of 500), matched by serial; the inventory wins; devices Nautobot doesn't have are ignored; an unreadable list keeps its last answer. Never on the board, never notified. `GET /api/locations/<id>/detail` answers `onboarding` per device. Schema version 31 (`wireless_pnp_status`). The demo's Stockholm has two such APs
- **Access points on the board, with their address from the wireless controller** (#521): access points get their address by DHCP, so a device a Catalyst Center or New Central lists is monitored without a primary IP in Nautobot, shown with the address the controller reports (never written to Nautobot), and down when the controller says so, until it is up again or its Nautobot status is excluded. A site with only access points down is at `WIRELESS_AP_LEVEL` (default `low`) under a new **Wireless** chip, not Alarms: after every alarm, not on the wall, a soft dot in the map's quiet clusters, never notified, Operational on the status page, out of availability and the activity feed. A device a controller lists is judged as an access point, whatever its role, and never waters down the share of the other devices down; nothing changes without `WIRELESS_CONTROLLERS_FILE`; more than 3 fold into one line on a row and into their own fold in the site panel. An unreachable controller's last answer stays, marked "last known". MCP's `get_alert_board` takes `filter=wireless`. Schema version 30 (`wireless_ap_status.ip`, `alert_instances.access_point`)
- **The map's site panel says who is on it** (#512): under the status line, "Case INC0048213" (linked to your ITSM with `CASE_URL_TEMPLATE`; the first three, then "+N"), and in red the down devices nobody is on (neither a case nor an acknowledgement): **No case**, or "29 without a case" when some have one; each down device shows its own case, as on the board. Read when the panel opens, by the location's devices (one query); `GET /api/locations/<id>/detail` answers `cases` and `cases_read`, and `case_numbers` and `acknowledged_by` per device with an open alert
- **The customer's circuits on their status page** (#511): under each site, folded, "▸ 3 circuits", opening to "DK-TELIA-123456 · Internet Transit · 1 Gbps": circuit ID, type and bandwidth, never the provider. Only circuits whose Nautobot tenant is the customer, and only Active ones; those that end at the site, or have no termination and its address as description. Read from the cached circuits, one query per page; `GET /api/status/<id>` answers `circuits` per site. Schema version 29 (`nautobot_circuit_cache.location_ids`), filled at the next sync
- **Access point status from HPE Aruba Networking New Central too, any number of instances** (#508): `aruba_central` in `WIRELESS_CONTROLLERS_FILE`, each with a `region` (us1, de1, …) or `base_url` and a Central-scoped API client from GreenLake (client id and secret; no refresh token to keep). Read in pages of 1,000 (`/network-monitoring/v1/aps`), matched like Catalyst Center's
- **Access point status from Cisco Catalyst Center, any number of instances** (#508): `WIRELESS_CONTROLLERS_FILE` lists them (a YAML file with read-only accounts and https URLs); each is read in bulk every `WIRELESS_SYNC_INTERVAL_SECONDS` (default 300), and its access points are matched to Nautobot devices by serial, else name. One the controller reports down is counted ("2 of 40 access points down" on the status page, also at an operational site, and in its headline), and on the board (#521, above). Each instance on its own: the top bar names one that can't be reached, `/metrics` has `nautobot_maps_wireless_access_points{controller,state}` and `…_matched{controller}`, and `python -m nautobot_maps wireless-check` says what each lists and matches. Schema version 28 (`wireless_ap_status`); PyYAML is a new dependency

### Changed
- **`token list` shows the tokens that work** (#528): the active ones, then "+N revoked or expired (--all to show)"; `--all` lists every token as before, `--tenant` only one tenant's. `GET /api/tokens` likewise lists the active ones unless `?all=true`, answers `inactive` (how many are revoked or expired) and takes `?tenant=`
- **Every configuration choice documented, and kept so** (#519): the wireless controllers have their own section in the configuration guide and a table of every key in the file (Catalyst Center, Aruba New Central); the README's "Add what you need" names access point roles, one row per Site and per-tenant device roles. Tests fail when a setting, a key of the wireless file or a command isn't documented
- **One `config/` folder for the app's files** (#517): `docker-compose.yml` mounts `./config` read-only at `/config`, so the wireless controllers file, criticality rules and CA certificates need no `docker-compose.override.yml` (e.g. `WIRELESS_CONTROLLERS_FILE=/config/wireless.yml`). The folder is git-ignored and kept out of the image. The app (uid and gid 10001 in the container, now an explicit group) reads it through its group: `sudo chgrp -R 10001 config && sudo chmod 2750 config`, files `640` (config/README.md). A file it can't read says so at startup, and what to run. The README's install ends with "Add what you need", and the setup docs point at `/config`
- **The status page says "6 network devices", not "6 network"** (#515): a site where all is well now reads "12 network devices · 40 access points" in full, like the lines with something down; Availability's table keeps its short "12 network · 40 APs"

### Fixed
- **A status token for a tenant Nautobot doesn't have is refused** (#528): `token create --role status --tenant` and `POST /api/tokens` answer `no tenant 'Acme' in Nautobot (as of the last sync)`, as `status-link` does, instead of making a link that shows nothing; the token keeps Nautobot's spelling of the tenant

- **Data contract** with Nautobot and LibreNMS (#309): `docs/data-contract.md` lists, per upstream endpoint, the fields the app reads, their types, and what each becomes in its tables (generated from `nautobot_maps/contract.py`: `python -m nautobot_maps contract-docs`). Every sync checks what it fetched against it: a missing or changed field is logged once per sync by name, counted in `/metrics` (`nautobot_maps_contract_mismatches{source,endpoint,field}`) and shown by `GET /api/contract`. CI checks it against a real Nautobot. New `contract_checks` table (schema version 10); a sync that fetched nothing (incremental, no changes) keeps the previous result. The demo's mock Nautobot now returns `last_updated`, as Nautobot does
- **LibreNMS alert pushes** for near-real-time status (#284): `POST /api/librenms/alert` (operator role; for LibreNMS's API alert transport with an API token) with a LibreNMS `device_id` or `hostname` refreshes that device from the LibreNMS API and rebuilds the board within seconds, instead of after the next LibreNMS sync. An older LibreNMS answer never overwrites a newer one (push or sync); unknown devices are not an error; a failed rebuild is retried by the next scheduler tick. Schema versions 8 and 9 (`librenms_device_status.pushed_at`, `push_seq`). Setup in `docs/configuration.md`
- **API tokens** for scripts, LibreNMS and MCP clients (#297): `Authorization: Bearer nmt_…`, each with a name, a role and an optional expiry; they work with `AUTH_MODE=disabled` and `header`, from any address, and changes are recorded as `token:<name>`. Only a SHA-256 is stored; the token is shown once. Managed with `python -m nautobot_maps token create|list|revoke` or `GET/POST /api/tokens`, `POST /api/tokens/<id>/revoke` (admin role); a wrong, expired or revoked token gets 401. New `api_tokens` table (schema version 7). See `docs/authentication.md`
- **Maintenance windows** for a whole site or some of its devices, now or planned ahead (#283). A site in maintenance shows MAINTENANCE "until … · reason" instead of its level (new Maintenance tile, an "In maintenance" section at the bottom of the wall view, blue on the map); a device in maintenance is left out of its site's level. The alert history is frozen for what a window covers, and nothing is notified until it ends. API: `GET/POST /api/maintenance`, `POST /api/maintenance/<id>/end` (operator role); new `maintenance_windows` table (schema version 6); `/api/alerts` `summary` has `maintenance`; managed from the board with the **Maint.** button on a site's row (start now, plan ahead, end or cancel), or `GET /api/maintenance/devices` for the devices that can be put in maintenance
- **Notifications** when a site's alert level changes: a site reaching `NOTIFY_MIN_LEVEL` (default Critical) and dropping back below it, to a webhook (JSON, optionally HMAC-signed), Microsoft Teams (Workflows webhook) and/or email (SMTP). Optional tenant filter; a burst of changes goes out as one summary. Messages are queued in the same transaction as the level change (`notification_outbox`, schema version 5) and sent by the background scheduler at least once (each event has a stable `id` for dropping duplicates), with retries; bursts become summaries of at most 25 sites; `/metrics` shows pending and failed messages; `POST /api/notifications/test` (admin) sends a test. See `docs/notifications.md` (#282)

### Security
- **Changes from another site are refused** (CSRF): behind a sign-in proxy a page elsewhere could make a signed-in user end a maintenance window, revoke an API token or send a test notification with a plain form. A change the browser marks as cross-site (`Sec-Fetch-Site`, else `Origin`) now gets 403. The app's pages, scripts, webhooks, API tokens and `/mcp` (its own `MCP_ALLOWED_ORIGINS`) are not affected
- **The bundled sign-in proxy** (#423): the session cookie is `SameSite=Lax`; users in many groups (about 150 Entra ID groups) no longer get a 500 from nginx's 4 KB header buffer; redirects use `PUBLIC_HOSTNAME`, not the request's Host
- **certifi 2026.10.19** (GHSA-6q48-6c7w-9gw2, critical): the CA bundle no longer trusts the emSign roots whose intermediate CA keys were compromised. The CI audit and the image scan failed on every PR until this update
- **No inline styles** (#370): the Content-Security-Policy's `style-src` is now `'self'` only, so injected HTML can no longer restyle a page (an overlay with a fake link); the map's markers and the error page use classes and a CSS file, and a test keeps inline styles out

### Fixed
- **The map opens on your sites, not the Arctic** (#459): a lone site far from all the others (e.g. one in northern Greenland beside a network in Europe) no longer stretches the first view and pulls it off-centre; the map frames the main group, and that site stays on the map. A real group of sites there is still framed
- **A browser MCP client from an allowed origin** (`MCP_ALLOWED_ORIGINS`) could read but not add cases or acknowledge: the tool's own call carried the browser's `Origin`, and was refused as a change from another site. /mcp already checks the origin (#436)
- **MCP tools saw nothing for clients asking for gzip**: the tools call the app's own API and copied the caller's `Accept-Encoding`, so the answer came back compressed and unreadable; most MCP clients send it. History, the board and the rest now come through (#436)
- **A chunked upload** (a request body without Content-Length) is read again under the new server (#436)
- **"May be misplaced" no longer flags correct sites on other continents** (#416): the map's coordinate check compares each site with the other sites in its own region of the Nautobot location tree ("EMEA › DNK", then "EMEA"), not with the middle of the whole network, and says what it compared with ("9,194 km from the other sites in EMEA › DNK"). The line under the map's count counts only sites that are missing or have wrong coordinates ("2 have wrong coordinates"); "far" sites are hints, last in the list under their own heading. The CSV's `km_away` column is now `km_from_centre`, with a new `compared_with` column; the API adds `compared_with`
- **Map place search** (#411): Enter searches within 5 km for cities, addresses and coordinates again, even with matching site suggestions; only a full site-name match opens a site. The map-search suggestion comes first otherwise.
- **A stack is one device** (#405): a switch stack is one logical device, so an IP on any member is the stack's and, when any of them doesn't answer, the whole stack is down. It counts once (as its master) on the board, the map and the site panel, and its line says "Stack sw-stack01: all 4 members down", Copy naming the members (not "master of 4"). A member is never down on its own: no more "member 2 of 4" or "Stack of 4 · 1 down". On upgrade, an open alert on a member with its own IP closes and the stack's opens
- **Stack members showed as "Unknown"** (#400): the members of a Nautobot virtual chassis often have no name. They are now named by their stack and place ("sw-stack01:2"), and the site panel shows a stack as one device, "Stack of 4" ("· 1 down" when a member is), its members listed when opened. The first sync after the upgrade is a full one
- **The tenant's (i) in the map's site panel shows its description** (#390): it opened behind the panel, so nothing seemed to happen; it is on top now. A click or tap keeps it open: before, a tenant's description (and an alert badge's reason) closed as soon as the pointer left it, and a tap on a tablet never kept it; now it stays until a click elsewhere, a second click, Escape or a scroll of what it is in, and Escape closes only the tip
- **The map's site panel has no Country row** (#386): with addresses like `Roersvej 33, 5000 Odense C` it showed the town; the Address row is there
- **A site's country was its town** (#386): with an address like `Roersvej 33, 5000 Odense C`, the map's Country row, the board's search and MCP took `5000 Odense C` as the country. The country now comes from Nautobot's country field, else a location of type Country above the site (`COUNTRY_LOCATION_TYPE`), else the address's last part only when it can be a country (no digits, not the town after a street or a postcode); otherwise none. Renaming or moving a location others are under makes the next sync a full one. The first sync after the upgrade is a full one that rewrites them
- **`COMPRESS_RESPONSES=false` was ignored under Docker** (#380): `docker-compose.yml` didn't pass it to the container, so the app kept compressing behind a proxy that does it; it is passed now, it is in `.env.example`, and the test that checks every setting reaches Docker also covers settings read as on/off flags
- **The map's search, site panel and location loading when the server answers with an error page** (#350): the message shows the API's error or the page's text, not a JSON parse error, as on the board
- **Adding a case when the server answers with an error page** (#350): the message shows the page's text, not a JSON parse error, as the other board actions do
- **The map and the alert board showed different levels** for a site with unmonitored devices (#316): the map's marker colours and its site panel counted every device, the board only those with a primary IP and not of an excluded status (and the panel ignored maintenance, the alert delay and flapping). Both now take a site's level from its board row ("2 down · 7 monitored" in the panel too); the panel marks devices that don't count and says why. A site whose only down devices are within the alert delay is OK on the board, not "no data"
- A location's **country** was worked out on every sync but not stored, so with PostgreSQL the map's Country row, the alert board's country filter and MCP's search by country found nothing. It is stored now (schema version 11); the first sync after the upgrade is a full one that fills it in (#309)

## [0.1.0] - 2026-10-09

The first release: Nautobot sites on a map, and an alert board that shows which sites are down, since when, and who has a case on them. The story behind each feature is in the referenced issues and pull requests.

### Map
- Every Nautobot location with coordinates on an OpenStreetMap map, coloured by alert level as soon as it loads (#234); clustering for large inventories and co-located sites grouped in one marker.
- Filters by status, location type, parent, tenant and tenant group; search by address or `lat,lon` for sites within 5 km.
- Site panel with devices, ASNs, circuits (#235), and each tenant's Nautobot description behind an (i) (#263).
- Tiles and address search can point at internal services (`MAP_TILE_URL`, `GEOCODER_URL`, `GEOCODER_ENABLED`) (#197).

### Alert board
- One row per site with its level, worked out from the monitored devices (those with a primary IP): **Critical** (a core device down, or all of them), **Medium** (more than 25% down), **Low**, **No data**, **OK** (#124). Core devices come from role keywords (`CRITICAL_ROLE_KEYWORDS`, `CRITICALITY_RULES_FILE`) and per-device overrides.
- Opens on **Alarms**; the summary tiles filter by level; search, tenant and sort (newest down first by default) on one line, status, type and non-operational sites under **More filters** (#242, #228).
- Device status from Nautobot and, optionally, LibreNMS, including the IP LibreNMS polls when Nautobot has none (#137).
- **Since** column: a site is "in alarm 3h 40m", a device "down 25m" (#275, #279).
- One row per Site with buildings and floors rolled up (`ALERT_BOARD_SITE_LOCATION_TYPE`), the location path under the name (#158, #178, #269).
- Every tenant of a site, including those linked by Nautobot Relationships, with "+N more" (#238, #279).
- Hide sites by location type, status, tag or name, and ignore devices by status (`ALERT_BOARD_EXCLUDED_*`) (#151).
- Updates itself: a background scheduler syncs and records history with no page open, and an open board reloads when the next sync is due (#154, #152).
- **Activity** panel: devices down and up, and site level changes (#180).

### Wall view
- `/alerts?view=wall` (**Wall view** in the top bar) for a NOC screen: sites with alarms and their down devices, address and cases, no controls (#243, #252, #248, #254).
- At a glance who is on it: **NO CASE**, **"1 of 2 no case"** or **✓ INC-1234**; sites with a case on every device turn grey and move below a dashed line (#271).
- Shows when it last updated, turns red after 10 minutes without an update, and keeps the last board under a red banner when it can't load (#243).
- Browser-standard text size; size a big screen with the browser's zoom (#267).

### Cases, history and export
- **+ Case** attaches a case number to a site's down devices; it shows existing cases and won't add the same number twice (#133, #273).
- **Copy** puts a site and its down devices on the clipboard for an ITSM ticket (#227).
- Alert history per device with downtime and cases; an alert starts when the device went down in Nautobot, and a level change doesn't restart it (#163, #166).
- **History** panel and CSV export per site for the last 7, 30 or 90 days or everything: one row per incident or per device (#277).
- `ALERT_HISTORY_RETENTION_DAYS` deletes old resolved history (#194).

### Integrations
- **MCP server** at `/mcp` for AI assistants, off unless `MCP_ENABLED=true`; its tools use the same sign-in and roles as the web UI (#250).
- **API explorer** at `/docs` with every endpoint and **Try it** (#230).
- Nautobot 2.x and 3.x; the app only reads from Nautobot, so a read-only token is enough (#188).

### Sign-in and roles
- Optional sign-in through a reverse proxy or SSO gateway (`AUTH_MODE=header`) with viewer, operator and admin roles from groups; identity headers are trusted only from `AUTH_TRUSTED_PROXIES`, optionally with a shared secret (#187, #188).
- Without sign-in the board works, but changing criticality overrides is refused unless `ALLOW_UNAUTHENTICATED_WRITES=true` (#188).

### Operations
- Docker image (`ghcr.io/jackass4life/nautobot-maps`) running as a non-root user, with a health check, Debian security updates installed at build time, and PostgreSQL in `docker-compose.yml` (#131, #246, #153).
- Versioned database migrations, applied once before the app starts; a database newer than the release is refused (#201).
- `/healthz` and Prometheus `/metrics` (sync state, open alerts and sites by level) (#200).
- Logging with stack traces for unexpected errors, an access log, and `LOG_FORMAT=json` (#193).
- Database connect and statement timeouts (#190); retries with backoff for Nautobot and LibreNMS (#192).
- Browser security headers, including a Content-Security-Policy that runs only the app's own scripts (#198).
- Hashed dependency lock files, and CI with tests against PostgreSQL, ruff, ESLint, `pip-audit`, `npm audit`, CodeQL and a Trivy scan of the image (#186).
- Documentation in `docs/`: configuration, the alert board, running in production (released images, backup and restore, upgrades), sign-in, MCP (#256).

### Upgrading from an earlier `main`
Only for installations that ran unreleased code from `main`:
- SQLite is no longer supported: move to PostgreSQL (`NAUTOBOT_MAPS_DATABASE_URL`) first; `NAUTOBOT_MAPS_DB` is ignored (#153).
- The Nautobot pass-through API (`/api/roles`, `/api/location-types`) was removed (#188).
- With `AUTH_MODE=disabled`, changing criticality overrides returns 403 unless `ALLOW_UNAUTHENTICATED_WRITES=true` (#188).
- `FLASK_SECRET_KEY` is ignored (#199).
- Database migrations run automatically at startup; take a backup first.
